# T-CaaS Image Provisioning Debugging

## Overview

Image provisioning in T-CaaS uses a chain of custom resources to declare which container images should be synced (mirrored) into cluster-local registries. Understanding how these CRs interact is essential for diagnosing image availability issues.

## Resource Chain

```
RawRegistry (declares a source registry)
    └── Image (declares a specific image to sync)
         └── RawSyncRequest (generated sync job for the image sync operator)
```

### RawRegistry

Defines a source container registry endpoint:

```yaml
apiVersion: registry.tcaas.telekom.de/v1alpha1
kind: RawRegistry
metadata:
  name: mtr-devops
spec:
  endpoint:
    url: mtr.devops.telekom.de
  auth:
    secretRef:
      name: mtr-pull-secret
```

### Image CR

Declares a specific image to be synced. References a RawRegistry and specifies source path, name, and tag:

```yaml
apiVersion: registry.tcaas.telekom.de/v1alpha1
kind: Image
metadata:
  name: t-caas-integrations-operator
  labels:
    registry.tcaas.telekom.de/architecture: amd64
    registry.tcaas.telekom.de/os: linux
spec:
  registryRef:
    name: mtr-devops
  source:
    path: cit/t-caas
    name: t-caas-integrations-operator
    tag: "main-abc1234"
```

### RawSyncRequest

Auto-generated by the image sync operator from Image CRs. Triggers the actual image copy.

## Path Construction

The full image reference is constructed as:

```
<registry.endpoint.url> / <source.path> / <source.name> : <source.tag>
```

Example:
```
mtr.devops.telekom.de/cit/t-caas/t-caas-integrations-operator:main-abc1234
```

Verify path correctness:
```bash
# Must resolve to a valid manifest
crane manifest mtr.devops.telekom.de/cit/t-caas/t-caas-integrations-operator:main-abc1234
```

## Common Label Mismatches

### Architecture: amd64 vs x86_64

The image sync operator uses labels to filter images by architecture. The correct label value is `amd64`, NOT `x86_64`:

```yaml
# CORRECT
labels:
  registry.tcaas.telekom.de/architecture: amd64

# WRONG - will not match sync filters
labels:
  registry.tcaas.telekom.de/architecture: x86_64
```

### Missing os-variant Label

Some images require the `os-variant` label to be set. If missing, the sync operator may skip the image:

```yaml
labels:
  registry.tcaas.telekom.de/architecture: amd64
  registry.tcaas.telekom.de/os: linux
  registry.tcaas.telekom.de/os-variant: ""  # Set empty string if not applicable
```

### Label Selector Debugging

Check which images the sync operator is selecting:

```bash
kubectl get images -l registry.tcaas.telekom.de/architecture=amd64
kubectl get rawsyncrequests -A
```

## Checking Image Sync Operator Logs

```bash
# Find the image sync operator pod
kubectl -n image-sync-system get pods

# Check logs for sync errors
kubectl -n image-sync-system logs -l app=image-sync-operator --tail=100

# Look for specific image
kubectl -n image-sync-system logs -l app=image-sync-operator --tail=200 | grep "t-caas-integrations-operator"
```

Common log patterns:
- `"image not found"` — source path or tag is wrong
- `"unauthorized"` — registry auth secret is missing or expired
- `"manifest unknown"` — tag does not exist in source registry
- `"skipped: label mismatch"` — architecture/os labels do not match filter

## Forcing Flux Reconciliation

When Image CRs are defined in a git repo managed by Flux, changes may not be picked up immediately.

### Reconcile Git Source

```bash
# List git sources
flux get sources git -A

# Force reconcile
flux reconcile source git <source-name> -n flux-system
```

### Reconcile Kustomization

```bash
# List kustomizations
flux get kustomizations -A

# Force reconcile
flux reconcile kustomization <kustomization-name> -n flux-system
```

### Full Chain Reconciliation

```bash
# Reconcile from source through to kustomization
flux reconcile source git platform-clusters -n flux-system
flux reconcile kustomization images -n flux-system

# Verify Image CR was updated
kubectl get image t-caas-integrations-operator -o yaml
```

## End-to-End Debugging Checklist

1. Verify the image exists in the source registry: `crane manifest <full-image-ref>`
2. Check the Image CR exists and has correct spec: `kubectl get image <name> -o yaml`
3. Verify labels match sync operator filters (architecture=amd64, os=linux)
4. Check RawSyncRequest was generated: `kubectl get rawsyncrequests -A | grep <name>`
5. Check image sync operator logs for errors
6. If Image CR is outdated, force flux reconciliation of the git source and kustomization
7. After sync completes, verify image is available in the local registry
